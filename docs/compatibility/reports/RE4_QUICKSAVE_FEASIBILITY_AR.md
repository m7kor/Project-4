# الحفظ الخارجي عند نقطة يختارها اللاعب

27 أكتوبر 2026. المطلوب الذي أكده المستخدم هو الرجوع إلى نقطة تقدم، مثل المنطقة الثانية، حتى لو كانت نقطة الحفظ الأصلية بعيدة. نسخ بطاقة الذاكرة وحده لا يحقق هذا الطلب.

**الحفظ السريع القابل للاسترجاع بعد إغلاق اللعبة غير منفذ حاليًا.** لم يُضف زر يوهم بأنه يحفظ نقطة قابلة للاستكمال، ولم تُكتب إحداثيات أو أعلام أو ذاكرة لاعب لتصنيع التقدم.

## ما حُفظ فعلًا من الجلسة الأخيرة

انتهت الجلسة `host-boundary-manual-01` بطلب المستخدم بعد 1079.516 ثانية. أُخذت نسخة مستقرة من بطاقة الاختبار قبل الإيقاف في `termination-evidence`، وبقيت البطاقة الأصلية للجلسة مساوية للنسخة التي بدأت بها. هذا يحمي آخر حفظ عادي؛ لا يحفظ الموقع الحالي عند 0x101.

توجد أدلة للعبور الطبيعي 0x100→0x101 و677 ملاحظة متتالية يتطابق فيها رقم الغرفة المطلوب مع رقم RoomData. توجد 914 صورة مثبتة بالبصمات و1576 حدث إدخال فعلي. هذه أدلة تقدم، وليست حالة محرك يمكن تحميلها.

تسجيل المسار يحتوي اختلافًا حقيقيًا واحدًا داخل نبضة الضيف نفسها: عند EE10419 تغيّر المحور من 135 إلى 137، مع ترتيب وتوقيت مضيف معروفين. واجهة replay الحالية تقبل فترات على مستوى field، فلا تستطيع تمثيل الحدثين بدقة. رفضها صحيح. لم يُسقط أحد الحدثين ولم يُستوفَ وقت ضيف افتراضي بينهما. لذلك لا يُقدَّم هذا المسار على أنه زر استكمال خارجي موثوق.

## ما يدعمه المصدر الحالي

| المكوّن | الموجود | الناقص للحفظ والاسترجاع الكامل |
|---|---|---|
| بطاقة الذاكرة | حفظ أصلي سبق اختباره، ونسخ معزولة وبصمات | إنشاء تقدم جديد بعيدًا عن نقطة الحفظ |
| RAM ونداء EE | التقاط integer-call في `ps2_runtime.cpp` | النص نفسه يصرح بأنه يستبعد FPU وطوابير الأجهزة وVU؛ لا توجد استعادة كاملة مقابلة |
| VU | لقطات replay ومقارنة حالة معمارية ومعلقة مفصلة | codec حفظ/تحميل وإعادة ربط المراجع ضمن حالة المحرك كله |
| EE والجدولة | سياقات وخيوط ومقاطعات ونقاط تعاون مع runtime | عقد إيقاف واستئناف موحد يضمن اتساق الاستكمال والحالة الحية |
| IOP وSIF وDMA وVIF | حالات تنفيذ واختبارات وإعادة تشغيل لحالات ضيقة | حفظ كامل للرسائل والإكمالات والانتظار والذاكرة والمقاطعات ثم استعادتها |
| GS وparaLLEl-GS | renderer قائم ومخرجات تشخيصية | إتمام الأعمال الجارية، وحفظ الحالة اللازمة وVRAM، وإعادة إنشاء موارد المضيف بأمان |
| SPU2 والصوت | PCM وتشخيص requested/delivered/underrun | سياق الصوت والجدولة والمزج والـdecoder، مع إعادة تهيئة خرج المضيف دون تشغيل عينات قديمة |
| الموارد والوحدات | تحميل أصلي ومسارات streaming | مواضع القراءة والطلبات المعلقة وهويات الوحدات وربط الموارد بعد الاستعادة |
| الإدخال والزمن | EE fields حقيقية وترتيب أحداث | توقيت أدق أو ordinal لكل قراءة pad؛ ثم اختبار حتمية الاستكمال |

لا يكفي نسخ ذاكرة العملية أو إيقافها: مؤشرات المضيف والـcallbacks والأقفال وموارد GPU ليست ملف حفظ محمولًا. كما لا يجوز تسمية hash observer أو RAM dump بحالة قابلة للاسترجاع.

## المسار الأصغر الذي يستحق التحقيق

إذا كان المطلوب الرجوع إلى **بداية المنطقة الثانية** بدل اللحظة الدقيقة، فقد يكون استعمال آلية الحفظ الأصلية للعبة أصغر من بناء savestate كامل. يلزم أولًا تحديد مسار إنشاء بيانات الحفظ وشروطه، وإثبات أنه يحتفظ بالغرفة والمخزون والأحداث بصورة يستطيع المحمّل الأصلي استعادتها. لم يُثبت بعد أنه يمكن استدعاؤه خارج تفاعل الحفظ المعتاد، ولم تُتجاوز شروطه بتعديل الذاكرة.

اختبار هذا المسار يجب أن يستخدم بطاقة تجريبية جديدة: الوصول الطبيعي إلى المنطقة، إنشاء حفظ عبر مسار مثبت، إغلاق العملية، تشغيل عملية جديدة، ثم مقارنة الغرفة والمخزون والذخيرة والتقدم والتفاعل. لا يُقبل نجاح الكتابة إلى ملف وحده. تبقى بطاقات المستخدم والنسخ المعتمدة خارج التجربة.

أما الاستكمال من اللحظة نفسها فيحتاج مشروع حفظ حالة منسقًا بين الأنظمة السابقة، بهوية إصدار صارمة وصيغة قابلة للتحقق واختبارات restore فعلية. التحقيق الحالي في أداء VU لا ينفذ هذا النظام ولا يعلن جاهزيته.
